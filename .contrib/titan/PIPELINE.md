# Titan Parser pipeline reference

This reference describes the experimental Parser integration branch built on the Phase and Titan runtime changes. CI validation and artifact provenance must be recorded for the exact tested head. Successful tool checks establish reproducible output and isolation; they do not verify Titan game loot or the installed client. See the [architecture plan](TITAN_DATABASE_PLAN.md) for evidence and remaining client checks.

## Inputs and progression are independent

The candidate Titan config is `.contrib/.db/standard/.config/classic/03 - Titan Reforged.config`. It composes the existing Retail base config with a complete Classic tag array, `DataPhase: WRATH`, candidate `DataPatch: [3,80,2,70372]`, isolated Wago inputs, and `db/Titan/` output. Ordinary Wrath ItemDB uses `WRATH_CLASSIC_ITEMDB`; Titan never enables that tag.

`DataPatch` selects existing version/timeline branches. `DataPhase` supplies historical authoring compatibility. Neither selects the current release baseline. The shared catalog `.contrib/.db/shared/.config/progression/bindings.json` qualifies acquisition scopes by source path and ancestry; `era.json`, `sod.json`, `wrath.json`, and `titan.json` map those scopes to their own namespaced releases. The configured defaults are `era:6`, `sod:8`, `wrath:4`, and `titan:6`. Changing a profile's `baseline` changes generated profile/build metadata, while compatible category bodies remain identical.

Bindings annotate existing authored variants. They do not copy old encounters, rewards, costs, or difficulties into a replacement SoD raid. In particular, Classic and Wrath Naxxramas share instance ID `754` but have different source files; MC difficulty `9` and SoD difficulty `201` remain distinct. The same NPC `227819` has separate Phase 4 Tier 1 and Phase 5 Tier 2 vendor occurrences. Preserve those occurrences instead of assigning a release to every occurrence of an NPC or item.

Only catalog-declared progression IDs are adapted within mapped scopes. Main releases explicitly declared here are Era `11–16`, TBC `17–21`, Wrath `30–33`, and SoD `1605–1612`; those declarations are data, not engine numeric ranges. `u=1`, `u=2`, other unavailable states, and undeclared subphase conditions remain separate. Existing SoD aliases remain the compatibility path for unmigrated scopes. Titan earlier MC/Naxx chronology is unmapped compatibility, not an inferred Phase 1 release. BT/Hyjal remain exported with `titan:unknown`, hidden by default.

## Unverified availability changes

The Wrath raw ItemDB change renames its `DBContext` from `WRATH` to `WRATH_CLASSIC_ITEMDB` so Titan does not inherit the ordinary Wrath capture. The captured item records are unchanged. Its generated guard must be regenerated by the CI-built Consolidator; do not edit generated ItemDB text.

The Ulduar source changes six callback occurrences for achievements `17340` and `17341`. With the Wrath progression profile, callbacks use `SetSourceAvailability` to update the originating acquisition route. Without that profile, the Wrath callback preserves the current master behavior: `u` is the removed state or `nil`, and `rwp` is `nil` or `30200`. Other Classic flavors keep the existing generated callback template. A separate `NOT TITAN_REFORGED` guard omits those callbacks from Titan output. Omitting them changes Titan's unavailable-state behavior and is an unverified availability policy, not merely a mechanical callback adaptation. No new item, boss, or achievement ID is introduced by these hunks, and no new in-game observation is claimed.

These changes and the provisional catalog mappings remain experimental on this Parser CI branch. The existing architecture documents and snapshot manifest retain their dated sources and record-level evidence gaps. CI success alone does not make the Titan availability changes ready for a data review.

## Bootstrap manifest and snapshot updates

[snapshot-manifest.json](snapshot-manifest.json) currently has `inputStatus: bootstrap`, `verificationStatus: provisional`, and `inputs: []`. There is no imported Titan ItemDB or Wago snapshot. The Parser still generates full shared/standard authored data; it does not create an empty ItemDB placeholder or copy ordinary Wrath raw data. Wago's Item endpoint returned HTTP 403 on 2026-10-20, so build availability is unknown.

Run from the repository root with Python 3.9 or later:

```text
python .contrib/titan/update-snapshot.py --help
python .contrib/titan/update-snapshot.py --locale enUS
```

The build is pinned by the manifest. To request only a deliberate table set:

```text
python .contrib/titan/update-snapshot.py --locale zhCN --tables Item ItemSearchName UiMap
```

A successful update replaces the entire Wago CSV set with the selected tables and one selected locale; it retains non-Wago manifest entries and directory documentation. It validates each table's expected schema, nonempty numeric unique IDs, quoting, and row width before replacing live inputs. Base-locale filenames are `{Table}.{build}.csv`; other locales use `{Table}.{locale}.{build}.csv`, which the existing Wago loader recognizes.

Each manifest input records its URL, requested build, target region, locale, acquisition UTC, SHA-256, row count, and `verificationStatus: unverified`. The URL request does not attest the response's actual client build or region; hotfix status remains unknown. A later download failure leaves the prior directory and manifest unchanged. A failed manifest replacement rolls back the directory. Concurrent manifest edits abort the update. If a process is interrupted between filesystem replacements, Parser hash validation fails closed; inspect any recoverable `.titan-backup-*` directory before retrying. A surviving `.titan-update.lock` must be checked against the recorded process before removal.

Before an eventual build change, update the candidate config and manifest deliberately, acquire matching inputs, and record provenance. The Parser rejects mismatched build/region, unsupported input kinds, stale hashes, unlisted CSV/raw inputs, wrong filenames, and Titan output without a recorded raw source. Imported inputs remain provisional pending independent game evidence.

An actual Titan ItemDB capture must use these distinct names:

```lua
DBContext = "TITAN_REFORGED";
DBFileName = "03 - Titan Reforged";
ItemDB = { -- actual captured records only
};
```

Store the real capture at `.contrib/.raw/ItemDB/3.80.2.70372 Titan Reforged - ItemDB.lua`, regenerate it with the existing Consolidator, and add an `itemdb` manifest entry with `path`, `build`, `region`, `locale`, HTTPS `url` to accessible evidence, `acquiredUTC`, raw `sha256`, `generatedSha256`, and `verificationStatus: unverified`. Set `inputStatus: candidate`. Do not add an empty capture just to satisfy the filename or manifest checks. The generated file is `.contrib/.db/standard/00 - Item DB/.dynamic/03 - Titan Reforged.lua`; it must begin with the generated `TITAN_REFORGED` preprocessor guard.

## CI binaries and focused tests

Build Parser only in the Windows CI job from the exact branch commit, using the current SDK-style .NET Framework `net48` project, its pinned NuGet dependencies, and `Release|x64`. Restore dependencies and rebuild into a fresh staging directory; do not restore the obsolete explicit-Compile project entries or use a previously checked-in executable as proof of this branch's source behavior.

The workflow uploads the complete fresh Parser runtime payload as `parser-windows-x64-<commit SHA>`. Its `build-manifest.json` records the repository, commit SHA, workflow run ID and attempt, build configuration/platform, and relative paths with SHA-256 for every payload file. Download that CI artifact for local inspection or subsequent Windows execution; do not rebuild the Parser binary locally. Preserve the run URL and verify the downloaded hashes against the manifest.

CI runs `Test-Parser.ps1` with the freshly built payload in its expected `.contrib/.tools` layout. The test loads the .NET Framework assembly and compiles `ParserIntegrationTests.cs` in 64-bit Windows PowerShell 5.1 (`powershell.exe`, not PowerShell 7 `pwsh`). Python snapshot tests run with simulated responses and failures; they do not perform a network import.

The compiled tests exercise actual config composition, preprocessing, raw input isolation, qualified source binding, raw `groups` traversal, unknown/malformed profiles, preservation of `u=1/2/3`, child-release exceptions, separate acquisition routes, and baseline-independent category data. They also prove another stable profile ID can be configured without an engine whitelist change. Results must identify the same head and binary manifest as the generated-output checks.

## Regenerate the Wrath ItemDB guard

CI builds the tracked Item Database Consolidator source with dependencies compatible with that run's Parser payload. The checked-in Consolidator can reference older assemblies, so do not combine its existing executable with newly staged DLLs and assume compatibility.

Use an isolated scratch layout containing only the unchanged Wrath capture with its renamed `DBContext` and the CI-built Consolidator runtime payload. Run the Consolidator there, retain the CI build logs and generated-file hash, and copy the generated `.contrib/.db/standard/00 - Item DB/.dynamic/03 - Wrath.lua` into the generation checkout. Verify that only the expected preprocessor guard changes and that the captured item body is identical. The `parser-validation-<commit SHA>` artifact contains the CI-regenerated Wrath ItemDB together with `db-artifacts.sha256` and the four progression diagnostic reports after a full run; generated databases remain in the separate `db` artifact. No local build or manual generated-file patch substitutes for this step.

## Generate fresh flavor outputs

Keep the initial run scoped to the four opt-in profiles. `--prepare` removes only the selected generated database directories in this checkout; use an isolated staging checkout containing no unsaved generated work.

```powershell
python .contrib/validate-db.py --prepare --flavors Vanilla VanillaSOD Wrath Titan
Push-Location .contrib\.tools
try {
    foreach ($profile in '01 - Classic Era', '01 - Classic SOD', '03 - Wrath', '03 - Titan Reforged') {
        & .\Parser.exe auto 'baseconfig=../.db/standard/.config/retail/retail.config' ('config=../.db/standard/.config/classic/' + $profile + '.config')
        if ($LASTEXITCODE -ne 0) { throw ('Parser failed: ' + $profile) }
    }
} finally { Pop-Location }
python .contrib/validate-db.py --flavors Vanilla VanillaSOD Wrath Titan --manifest generated-four.sha256
```

`auto` enables unattended operation. Check each run reached both `ExportAddonData` and `FinalLogging`; do not infer completion solely from the process exit code or existing files. Preserve per-run logs and executable/input hashes. `.contrib/.db/build - all.bat` and `build - classic - all.bat` include Titan for normal production routes. Additional production flavors should be regenerated and verified separately with the same freshly compiled Parser as required by the change.

Every opt-in run writes actual binding hit counts to `.contrib/Debugging/Progression/{era,sod,wrath,titan}.json`. These ignored reports identify neutral key, source path, selectors, mapped phase, and hit count. They are diagnostic artifacts outside the addon database; no private provenance fields are emitted into acquisition nodes. Unmatched enabled bindings warn during generation and fail the generated-output validator.

## Validate real generated output

Run Lua tests only with Lua 5.1. After generating the four profiles and retaining the diagnostic reports:

```text
python .contrib/titan/validate-generated.py --repo-root . --lua lua5.1
lua5.1 .contrib/titan/titan-flavor-loading.lua .
lua5.1 tests/flavor-progression.lua .
```

Use the actual Lua 5.1 executable path if it is not on `PATH`. The generated validator executes actual `Instances.lua` and `Promotions.lua` category callbacks with inert constructors. It checks MC/BWL/Naxx legacy versus SoD reward paths, separate Phase 4/5 occurrences of NPC `227819`, child release exceptions, Titan roadmap and unknown mappings, the existing version-dependent mount `1280400` and titles `673–675`, preserved `u=1/2`, every enabled selector's real hit, and absence of private binding fields. These are source-to-output regressions, not new gameplay evidence.

For a full baseline independence check, preserve the generated Titan `Categories` directory, change only `titan.json`'s baseline (for example `titan:6` to `titan:5`), regenerate Titan with identical executable/data inputs, and compare:

```text
python .contrib/titan/validate-generated.py --repo-root . --lua lua5.1 --flavors Titan --compare-categories PATH_TO_PHASE6_CATEGORIES db/Titan/Categories
```

Restore the configured `titan:6` baseline and regenerate final artifacts afterward. The active profile/build metadata may differ; category bodies must be byte-identical. No test changes the actual server phase or claims earlier unknown loot was validated.

Before importing generated output, verify all referenced XML targets exist, all generated Lua compiles with Lua 5.1, and transferred file hashes match the verified Windows outputs. Preserve full outputs generated from authored sources; never substitute minimal database stubs for a failed build. Download verified generated outputs and CI binaries as artifacts; this branch does not automatically publish them or update release workflows.
